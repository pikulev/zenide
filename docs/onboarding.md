# Карта системы

Этот файл отвечает на вопрос «как оно устроено и почему так», а не «какую
команду набрать». Он для того, кто пришёл в репозиторий первым днём: читается
до [install.md](install.md) и до правок.

Разделение файлов такое:

| Файл | О чём |
|---|---|
| **onboarding.md** | ты здесь. Поставка: что куда кладётся и почему именно так |
| [architecture.md](architecture.md) | механика моста: Helix, tmux как шина, протокол инъекции |
| [extending.md](extending.md) | как дописывать под себя |
| [pitfalls.md](pitfalls.md) | грабли, которых не видно из кода |
| [install.md](install.md) | команды |

## 1. Две половины и два установщика

В репозитории живут две независимые вещи:

| Половина | Что это | Нужна ли другой |
|---|---|---|
| **zenide** — `bin/` `libexec/` `ide/` `modules/` `profile/` | терминальная IDE: Helix в центре, tmux как шина | самодостаточна |
| **дотфайлы шелла** — `shell/` `Brewfile*` `bootstrap.sh` | личное окружение одной машины macOS | zenide без неё работает |

Граница проходит по установщикам, и это самое полезное, что стоит понять
сразу:

```
 ./install.sh            ПРОЕКТ — работает у любого человека
 ────────────            ──────────────────────────────────────────────
 • 4 симлинка + якорь профиля          обратим: манифест + --uninstall
 • profile/*.example → *.local         пакетов НЕ ставит
 • --with: конфиги соседей слоями      окружение НЕ трогает
 • в конце гоняет zenide doctor

 ./bootstrap.sh          МАШИНА ВЛАДЕЛЬЦА — только у него
 ──────────────          ──────────────────────────────────────────────
 • софт: brew bundle по обоим Brewfile      НЕобратим: вне манифеста
 • рантаймы: rust (rustup), всё прочее mise сетевое, идемпотентно,
 • шелл: oh-my-zsh, тема, ~/.zshrc          падения печатаются как ⚠
 • ──▶ зовёт ./install.sh со всеми слоями   пошагово — install.md
```

Вопрос на каждый новый шаг установки: **это про проект или про эту конкретную
машину?** Симлинки и профиль — `install.sh`. Софт, рантаймы, шелл —
`bootstrap.sh`.

Важно, чего в `bootstrap.sh` НЕТ: выбора инструментов. Какой git-TUI, какой
файловый менеджер, какой редактор — это слоты в `profile/modules.conf`, и они
работают одинаково у всех. Деление «ядро vs личное» есть и в пакетах:
`Brewfile` — то, без чего zenide не работает (держать коротким),
`Brewfile.full` — личный стек поверх.

Личный `bootstrap.sh` явно устанавливает `all,git,mise,prettier` и загружает
шелл через якорь `${XDG_CONFIG_HOME:-$HOME/.config}/zenide/shell`. При переезде
клона он обновляет строку `SHELL_CONFIG_ROOT` в `~/.zshrc`, в том числе с
`export` и отступами, сохраняя остальные строки. Если `.zshrc` — симлинк,
редактируется его цель, сама цепочка ссылок остаётся на месте. Битая ссылка
или ошибка записи останавливает bootstrap; ошибка `install.sh` также не
даёт перейти к миграции шелла. Проверки — `tests/t-bootstrap.sh`.

`install.sh` голый **по умолчанию, а не по возможностям**: `--with all` даёт
ровно те конфиги соседей, что стоят у владельца, и тогда разница с
`bootstrap.sh` остаётся только в софте и окружении.

## 2. Четыре симлинка и кто их читает

После `./install.sh --apply`:

```
        ~/.config/                               <клон>/   (где угодно)
        │                                        │
        ├── zenide ─────────────────────────────▶ .              ← корень репо
        ├── tmux ───────────────────────────────▶ ide/tmux/
        ├── zenide-profile ─────────────────────▶ profile/
        │                                        ├── libexec/
        ├── helix/     ← ТВОЙ, не тронут         ├── modules/
        ├── yazi/      ← ТВОЙ, не тронут         └── bin/zenide
        └── lazygit/   ← ТВОЙ, не тронут               ▲
                                                       │
        ~/.local/bin/zenide ───────────────────────────┘

        ~/.local/state/zenide/manifest   ← журнал: что создали, что сдвинули
                                           СНАРУЖИ клона — иначе снёс репо и
                                           откатывать нечем
```

Симлинк заводится только там, где **кто-то читает путь жёстко** и вычислить
его не может:

```
 симлинк                      кто читает                   почему иначе нельзя
 ───────────────────────────  ───────────────────────────  ─────────────────────────
 ~/.config/tmux            →  tmux при старте              tmux смотрит только сюда
                                                            (либо в ~/.tmux.conf)

 ~/.local/bin/zenide       →  ты из шелла                  чтобы `zenide` была
                                                            командой

 ~/.config/zenide          →  tmux.conf, хуки, попапы,     в попапе tmux PATH НЕ
                              yazi, lazygit, tig, scooter   гарантирован → нужен
                              ("…/zenide/bin/zenide open")  стабильный абсолютный
                                                            путь

 ~/.config/zenide-profile  →  git `include.path`,          git НЕ раскрывает
      («якорь профиля»)       tmux `source-file`            $ПЕРЕМЕННЫЕ в
                                                            include.path, только `~`
```

Всё остальное путей не хардкодит, потому что `zenide` находит себя сам:

```
   ты набрал:  zenide open src/main.rs
                   │
   PATH ──────▶ ~/.local/bin/zenide        ← симлинк
                   │  readlink в цикле while (bin/zenide)
                   ▼
               <клон>/bin/zenide           ← реальный файл
                   │  dirname + "/.."
                   ▼
   ZENIDE_ROOT = <клон>        ← дальше все пути только отсюда
```

Цикл, а не `readlink -f`: последнего нет на части macOS, а цепочка бывает
длиннее одного звена. Следствие — **клон можно положить куда угодно.**

### Якорь профиля: один симлинк, два режима

```
 РЕЖИМ A — дефолт: профиль ВНУТРИ клона
 ─────────────────────────────────────────────────────────────────────
 ~/.config/zenide-profile ────▶ <клон>/profile/
                                  ├── theme.conf      ─┐
                                  ├── modules.conf     ├ трекаются, НЕЙТРАЛЬНЫ
                                  ├── projects.conf   ─┘
                                  ├── modules.local   ─┐
                                  ├── projects.local   ├ .gitignore — твоё
                                  └── git.local       ─┘
          снёс клон → профиль уехал вместе с ним

 РЕЖИМ B — профиль СНАРУЖИ клона
 ─────────────────────────────────────────────────────────────────────
 ~/.config/zenide-profile/      ← РЕАЛЬНЫЙ каталог, не симлинк
     ├── theme.conf                 install.sh его увидит и скажет
     └── git.local                  «внешний профиль на месте, не трогаю»

          снёс клон → профиль ЖИВ, переустановка подхватит его
```

Установщик различает «мой симлинк» и «реальный каталог пользователя»: второй
главнее и в бэкап не уезжает.

Резолв профиля в рантайме — три ступени, первая подходящая выигрывает:

```
   $ZENIDE_PROFILE задан?  ──да──▶  берём его
            │                       └─ так работают ./try, тесты, запись демо
            нет
            ▼
   ~/.config/zenide-profile есть?  ──да──▶  берём его   ← обычная установка
            │                                  (симлинк или каталог — неважно)
            нет
            ▼
   $ZENIDE_ROOT/profile    ← свежий клон, install.sh ещё не бежал
```

Профиль живёт снаружи клона по двум причинам: личное переживает снос и
переустановку репозитория, а форкеру не конфликтовать с апстримом на
`git pull`. Цена — дрейф схемы профиля в диффе не всплывёт, поэтому при
создании профиль помечается `.zenide-version`, и расхождение ловит
`zenide doctor`.

### Затенение: установка стоит, но не действует

Худший класс поломки — симлинки на месте, а конфиг не читается вовсе:

```
   tmux при старте ищет (man tmux, FILES):

     1. ~/.tmux.conf                  ◀── ЕСТЬ? читаем его и ОСТАНАВЛИВАЕМСЯ
                                           (oh-my-tmux, tpm — классика)
     2. ~/.config/tmux/tmux.conf      ◀── до сюда не дойдём НИКОГДА
            ▲
            └── наш симлинк на месте, но его просто не читают
```

`~/.gitconfig` устроен иначе: Git читает оба глобальных файла, а значения из
`~/.gitconfig` могут переопределять XDG-конфиг. Источники видны через
`git config --global --list --show-origin`. В разделе «затенение» doctor
предупреждает о возможном конфликте; одно наличие файла не доказывает
поломку. Для tmux нужно проверить, подключает ли старый конфиг zenide через
`source-file ~/.config/tmux/tmux.conf`.

## 3. Роль `ide/`: интеграция живёт в конфиге соседа

`ide/<тул>/` — вендоринг конфигов соседних инструментов. Главное в нём —
направление зависимости:

```
        ЯДРО                                       СОСЕДИ
   libexec/zenide/                        ide/yazi/ · ide/lazygit/ · ide/tig/
   ─────────────────                      ──────────────────────────────────
   знает слоты по РОЛИ:                   знают zenide ПО ИМЕНИ:
   editor · files · git_tui · search      "…/bin/zenide open ФАЙЛ СТРОКА"
            │                                            │
            │  не знает, что yazi — это yazi             │
            └──────────────── ◀───────────────────────────┘
                        звонок снизу вверх
```

Ядро никого не патчит и не оборачивает: конфиг соседа сам переопределяет свой
«открыть файл» на вызов диспетчера. Поэтому `yazi` остаётся обычным `yazi`, а
заменить его на другой тул — значит написать новый `ide/<тул>/`, не трогая
`libexec/`.

Как звонок доезжает (здесь и смыкается с [§2](#symlinks)):

```
 yazi: Enter на файле
   │   ide/yazi/yazi.toml
   ▼
 "${ZENIDE_ROOT:-$HOME/.config/zenide}/bin/zenide" open "$1"
    │                    │
    │                    └─ ФОЛБЭК: якорь-симлинк, если тул запущен вне tmux
    └─ из tmux: setenv -g ZENIDE_ROOT "$HOME/.config/zenide"
                                │
                                ▼
                  zenide open → найти пейн с hx → инъекция в его
                                командную строку → переключить окно
```

### Что внутри одного каталога

```
 ide/lazygit/
 ├── CONTRACT.yml  ← МИНИМУМ, нужный ЯДРУ (os.edit → zenide open).
 │                    Врезается в ТВОЙ конфиг. Ставить ничего не надо.
 └── config.yml    ← ПОЛНЫЙ: контракт + вкус (тема, delta, раскладка).
                      Вот это уезжает симлинком в ~/.config/lazygit.

              config.yml  ⊇  CONTRACT.yml
              └───────────────────┘
          вложенность проверяет tests/t-install.sh — грепает каждую
          значимую строку контракта в полном конфиге, иначе выжимка
          молча стала бы ложью
```

Отсюда главная мысль поставки: **ядру от соседа нужны одна-две настройки, а не
владение его конфигом.** Полный `ide/<тул>/` — референс-реализация и вкус; у
кого есть свой конфиг, берёт только `CONTRACT*`.

Контракты бывают двух природ:

```
 ТИП 1 — ОБРАТНЫЙ ЗВОНОК          yazi · lazygit · tig · scooter
 ─────────────────────────        «вызывай zenide вместо $EDITOR»
                                  нет → тул поднимет ВТОРОЙ инстанс редактора
                                        поверх себя, мимо всей шины

 ТИП 2 — ТРЕБОВАНИЕ СОХРАННОСТИ   helix
 ─────────────────────────────    «включи auto-save.focus-lost = true»
                                  нет → :reload-all затрёт НЕСОХРАНЁННОЕ
                                        (при уходе из hx буферы ещё не на диске)
                                  это про данные, а не про удобство
```

Асимметрия логичная: `helix` — получатель инъекции, он никуда не звонит, и его
контракт не вызов, а инвариант. Оба типа проверяет `zenide doctor`, раздел
«требования к соседям».

В `ide/` лежат не только конфиги, но и адаптеры: `ide/tig/hx-goto.sh`
переводит вызов `+42 файл` (vi-стиль) в `файл:42`, которого хочет helix.
Почему здесь, а не в `libexec/`: это особенность конкретного соседа, а не
механика ядра — уедет вместе с ним.

### `ide/LAYERS` — паспорт каждого каталога

```
   завёл ide/<тул>/  ──обязан──▶  строку в ide/LAYERS
                                         │
                        ┌────────────────┴────────────────┐
                        ▼                                 ▼
                   install.sh                          doctor
              (что ставить, что входит в        (что проверять и
               --with all, что требует           «что сейчас чьё»)
               явного согласия)
```

Это **данные, а не код**: список тулов нельзя дублировать в скриптах — он
протух бы в день добавления каталога в `ide/`. Градация идёт ровно по тому,
что сломается без конфига (четвёртая колонка `LAYERS`):

```
 слой       что будет без конфига zenide                   в --with all?
 ─────────  ─────────────────────────────────────────────  ─────────────
 core       zenide нет вообще (tmux — это и есть шина)     всегда
 contract   ядро ломается; нужна пара настроек             ✓
 slot       тул просто работает сам по себе, ядро цело     ✓
 taste      ничего: оформление и удобство                  ✓
 global     меняет поведение ЗА пределами IDE              ✗ только поимённо
```

Поимённо — это про `git` (editor, fetch.prune, identity), `prettier`
(форматирование всех проектов без своего `.prettierrc`) и `mise` (версии
рантаймов и LSP во всех проектах машины). Такое нельзя брать пакетом
«поставь всё».

## 4. Почему это можно ставить поверх своих конфигов

Исходная посылка названа в шапке `install.sh`: человек ставит **чужой** сетап
поверх **своих** конфигов. Из неё выведены семь механизмов.

1. **Умолчание — НИЧЕГО не делать.** `./install.sh` печатает план и выходит.
   План СОБИРАЕТСЯ целиком до печати и только потом исполняется: иначе
   «покажи, что сделаешь» неотличимо от «делай и комментируй».
2. **«Попробовать» ≠ «установить».** `./try` — весь сетап в песочнице:
   отдельные HOME/XDG и сокет tmux, профиль нейтральный (без твоих
   `*.local`). Это изоляция окружения; доступ к файлам проектов не ограничен. И сама печатает, чем отличается от
   реальной установки: песочница, выдающая себя за установку, хуже
   отсутствия песочницы.
3. **Градация вторжения — данные, а не код.** [`ide/LAYERS`](../ide/LAYERS),
   см. [§3](#ide). `global` не входит в `--with all`.
4. **CONTRACT вместо захвата конфига.** Ядру нужны одна-две настройки
   соседа ([§3](#ide)). Свой конфиг можно не отдавать.
5. **Обратимость: бэкап + манифест.** Чужой файл, каталог или симлинк
   сдвигается в `*.backup.<случайный-id>/value`. Манифест снаружи клона —
   журнал операций. Откат исполняет его в обратном порядке без дедупликации:
   после двух установок возвращается состояние ДО первой. Запись удаляется
   только после успешного шага; при ошибке остаток журнала сохраняется.
6. **Откат сохраняет изменения.** Ссылка удаляется, только если её цель
   совпадает с записанной. Копия — только если совпадает отпечаток содержимого.
   Изменённое или неизвестное переезжает в `*.saved.<случайный-id>/value`,
   затем возвращается исходный бэкап. Старые копии без отпечатков тоже
   сохраняются. Созданные личные файлы профиля остаются на месте. Правки
   клона не блокируют снятие симлинков: сами файлы клона не удаляются.
7. **`doctor` снимает не риск, а НЕИЗВЕСТНОСТЬ.** Раздел «что сейчас чьё» —
   построчно по `LAYERS`: zenide (симлинк на клон) / zenide (копия,
   `--copy`) / твой — zenide его не трогает / чужой симлинк / нет. Плюс
   перечисление найденных `*.backup.*` и раздел
   [«затенение»](#shadowing).

В `--copy` ядро и выбранные конфиги копируются. Входная команда
`~/.local/bin/zenide` остаётся ссылкой, но ведёт в УСТАНОВЛЕННОЕ ядро
`$XDG_CONFIG_HOME/zenide/bin/zenide`, а не в исходный клон. Профиль-копия
остаётся пользовательским каталогом и при откате не удаляется. Это нужно
тем, кого смущает, что симлинк на живой клон делает `git pull` изменением
боевого конфига:

```
   ./install.sh --apply  (link)              ./install.sh --copy --apply
 ────────────────────────────────          ────────────────────────────────
  ~/.config/tmux ──▶ <клон>/ide/tmux/       ~/.config/tmux/  ← реальная копия

   git pull в клоне = боевой конфиг          git pull в клоне = ничего
   изменился ПРЯМО СЕЙЧАС                    обновление — явная команда
```

Три честные оговорки, без которых список выше был бы обещанием, а не
описанием:

- **вне отката** остаются brew-пакеты, oh-my-zsh, TCC-права и побочные эффекты
  модулей раскладки — манифест их не ведёт и вести не может;
- **чужой симлинк** на месте конфига (stow, chezmoi, yadm) сдвигается в бэкап
  стрелкой, а не содержимым: `mv` симлинк не разыменовывает, поэтому откат
  возвращает именно её, вместе с прежней целью;
- обещания из этого раздела проверяются тестом `tests/t-install.sh` — правило
  проекта: свойство безопасности без теста не обещается, потому что ломается
  оно молча и выясняется на чужой машине.

## 5. Куда дальше

Опциональный `doctor --ui` хранит Python-окружение отдельно:
`${XDG_DATA_HOME:-$HOME/.local/share}/zenide/doctor-venv`. Оно устанавливается
явной командой `uv sync --locked` по `libexec/zenide/ui/pyproject.toml` и
`uv.lock`; библиотеки Textual не становятся глобальными CLI или зависимостью
ядра. `install.sh` не скачивает окружение и не ведёт его в манифесте, `--copy`
его не переносит. После обновления зависимостей синхронизацию нужно повторить.
Запуск doctor не обращается к сети. Инструкции — в [install.md](install.md).

Оформление — файл профиля: `doctor.tcss.local.example` поставляется с ядром,
`install.sh` создаёт из него личный `doctor.tcss.local`, если файла ещё нет.
У старого внешнего профиля без этого файла интерфейс берёт пример из ядра.

| Хочу | Куда |
|---|---|
| понять механику моста (зачем tmux как шина) | [architecture.md](architecture.md) |
| поставить | [install.md](install.md) |
| дописать под себя | [extending.md](extending.md) |
| не наступить на известное | [pitfalls.md](pitfalls.md) |
| узнать, что сейчас с моей машиной | `zenide doctor` |
