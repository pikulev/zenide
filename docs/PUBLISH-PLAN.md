# Публикация: из дотфайлов в проект-seed

> Статус: этапы 1–6 и безопасная поставка (§9) выполнены на ветке
> `publish-seed`. Осталось: демо (7), паблик (8), посты (9). Имя — `zenide`.

## 1. Рамка

**Что публикуем:** модульную терминальную IDE — helix в центре, tmux как шина,
yazi / lazygit / scooter / попапы как заменяемые слои.

**В какой форме:** seed. Форкаешь — он твой. Не библиотека, не дистрибутив.

Два правила, которые снимают противоречие между «готово из коробки» и
«допиливается под себя»:

> **Подавать как seed. Строить как библиотеку.**
>
> *Подавать как seed* — про обещания. README говорит прямо: форкай и присваивай,
> свой форк поддерживаешь сам, ломающие изменения возможны. Чужие issue — не
> обязательство. Это сказать нужно сразу, иначе репозиторий превращается в
> неоплачиваемую поддержку.
>
> *Строить как библиотеку* — про внутреннее устройство, и делается это **для
> себя**: слой `profile/` нужен, чтобы личное не размазывалось по механике.
> Побочный эффект — у форкера работает `git pull upstream`, пока он правит
> только `profile/`. Это не обещается, просто не ломается.

> **Публичный проект = рабочий сетап, а не его копия.**
>
> Один репозиторий, которым живёшь каждый день. Любая схема с отдельным
> «публичным ядром» создаёт шаг портирования, а шаги портирования гниют: через
> месяц публичное отстаёт, через три это мёртвый репозиторий со скриншотом.
> Поэтому — никаких релизных веток и бэкпортов. Пушишь как раньше.

Невидимым остаётся микроскопически мало: корни проектов с названием
работодателя, identity в git, прокси-алиасы. Всё — в `profile/*.local` под
`.gitignore`.

## 2. Что публично ценно

Фильтр: **дефицит** (этого нет больше нигде, люди ищут и не находят) против
**коммодити** (есть в тысяче репозиториев дотфайлов). Нужен, чтобы не
распылять усилия на вылизывание коммодити.

Коммодити — ремап prefix, сплиты и `hjkl`, session-per-project, темы,
`Brewfile`, обвязка zoxide/eza/fzf. Должно быть, ценности не создаёт.

Дефицит, по убыванию:

1. **Инъекционный мост в helix** (`hx-open.sh`). У helix нет remote-API — это
   открытая и регулярно задаваемая проблема сообщества. Неочевидно каждой
   деталью: bracketed paste одним кадром, `sleep 0.1` после Escape (иначе ESC
   склеивается в Alt-char), порядок `open → reload → goto`, флаг
   `@hx_skip_reload` как протокол против гонки с хуком. **Главный артефакт.**
2. **Чтение состояния из helix** (`hx-ctx.sh`). Ещё менее очевидно, чем запись.
   Именно оно делает возможным весь слой «заглавная буква = прыжок с контекстом».
3. **Самосборная справка** (`keys.sh`). Ценна независимо от helix — работает в
   любом tmux. Тезис: справку невозможно рассинхронить, потому что своих данных
   у неё нет. Самый дешёвый в потреблении артефакт.
4. **Blame-попап** (`hx-blame.sh`). `git log -L` с якорем на sha + номер строки
   *в той ревизии*, склейка с `bat`, навигация на `--with-nth 4..`.
5. **Корпус граблей** (`config/tmux/AGENTS.md`). `display-popup` не раскрывает
   `#{}`; `#()` считается только при отрисовке у клиента; голый `;` в
   `send-keys`; `less -F` закрывает одноэкранный попап. Создаёт доверие быстрее
   README: видно, что это эксплуатировали, а не написали в выходные.
6. **Кириллические двойники** (`cyr-twins.sh`). Аудитория узкая, проблема
   реальная, подход (двойник на *каждый* бинд, включая будущие) красивый.
7. **Архитектурный тезис.** tmux как шина IPC, редактор как заменяемый
   компонент, инструменты как модальные попапы, клей как маленькие скрипты,
   «регистр клавиши = смысл». Без него пункты 1–6 — набор скриптов.

Усилия: 1, 2, 7 — заголовок. 3, 4 — самостоятельные приманки. 5 — доверие.
6 — бонус-модуль.

## 3. Три слоя и правило отнесения

**На каждую правку один вопрос: это механика или вкус?**

- Вкус, личное, пути, идентичность → `profile/`
- Механика, соглашение, протокол → `libexec/` или `ide/`
- Не получается решить → `profile/`. Ядро должно оставаться маленьким; ошибка
  в эту сторону дешевле.

### Слой 1 — механика (ядро)

Переносимо как есть, личных данных ноль, зависит только от наличия тулов:
`hx-open`, `hx-ctx`, `hx-reload`, `hx-go`, `hx-files`, `hx-search`, `hx-diff`,
`hx-blame`, `yazi-here`, `lazygit-here`, `git-status`, `keys`.

### Слой 2 — композиция и соглашения

`tmux.conf:1-147` и `config/tmux/AGENTS.md`:

- сессия = проект, окна = контексты, попапы = одноразовые действия;
- **регистр клавиши = смысл**: строчная «переключиться», заглавная «прыгнуть с
  контекстом текущего файла» (`e/E`, `g/G`, `D`, `B`);
- окна ищутся по имени (`=yazi`, `=lazygit`, `=search`) или по процессу
  (`pane_current_command == hx`), не по номеру — за счёт этого тулы заменяемы;
- `-N "группа: описание"` на каждом бинде + `# keys:`/`legend=` в скриптах —
  единственный источник данных для справки.

### Слой 3 — личное

- идентичность: `config/git/config:2-3`, `editor = code --wait` (поправить на `hx`);
- машина и работа: `sessionizer.sh:10-15` (корни проектов, включая рабочий монорепо),
  `sh/parts/v2ray.sh`, `bin/pcap2flows`, sshfs + fuse-t + TCC;
- язык и железо: `abc.sh`, `cyr-twins.sh`, `cyr-map.txt`, `keyboard/` — два
  модуля, по умолчанию выключены;
- вкус: Monokai Pro Spectrum (`tmux.conf:148-167`, темы helix/yazi/gitui);
- стопка: `Brewfile` целиком, `NODE_VERSIONS` и per-version LSP-глобалы;
- легаси: `iterm2.itermexport`, `alacritty*.toml`, `config/nvim/`.

Нарушений правила в текущем репозитории ровно два: `sessionizer.sh:10-15` и
`config/git/config:2-3`. Всё остальное уже лежит правильно.

## 4. Целевая структура

Главный структурный ход: скрипты лежат в `config/tmux/` **не потому, что они про
tmux**, а потому что tmux умеет найти их по `~/.config/tmux/`. XDG-хвост машет
собакой — продукт спрятан внутрь конфига одного из инструментов. Мост не часть
конфига tmux; tmux им лишь пользуется.

```
<name>/
├── README.md  LICENSE  CHANGELOG.md
│
├── bin/<name>                     ← единственный entrypoint, уходит на PATH
├── libexec/<name>/                ← ЯДРО. Механика. Это и есть продукт
│   ├── editor/helix/{open,ctx,reload,goto}   контракт редактора, 4 операции
│   ├── files  grep  blame  diff             fzf-попапы
│   ├── window  jump                         окна по имени / прыжок с контекстом
│   ├── project  status  keys  doctor
│   └── lib/{tmux.sh,fzf.sh,ui.sh}           общее
│
├── ide/                           ← КОМПОЗИЦИЯ. Симлинкуется в ~/.config/<tool>
│   └── tmux/  helix/  yazi/  lazygit/  ghostty/  scooter/  git/
│
├── modules/                       ← OPT-IN поведение, по умолчанию выключено
│   ├── keyboard-force-latin/      латиница на любом переходе (нужен macism)
│   └── keyboard-cyrillic-twins/   двойники prefix-биндов, cyr-map.txt, layout/
│
├── profile/                       ← ВКУС. Первое, что правит форкер
│   ├── theme.conf  projects.conf  local.conf  modules.conf
│   └── *.local.example            identity, прокси → реальные под .gitignore
│
├── shell/                         zshrc.sh, parts/, theme/, bin/
├── tests/                         headless: tmux -L test + capture-pane
├── Brewfile  Brewfile.full        ядро (~12 тулов) / полный стек
├── install.sh
└── docs/
    ├── architecture.md  contracts.md  pitfalls.md  extending.md  install.md
    └── demo/*.cast
```

Что это даёт:

- `tmux.conf` из скриптовой свалки превращается в декларацию:
  `bind -N "git: дифф ханка" D display-popup -E "<name> diff"`;
- мост отвязывается от tmux концептуально — `<name> open src/a.ts:42` работает
  из шелла, из yazi, из helix, в теории под zellij;
- появляются `doctor`, `keys`, `help`, `--version` — то, что отличает инструмент
  от сборника скриптов;
- общий код в одном месте: протокол «Escape → sleep → bracketed paste» сейчас
  живёт в `hx-open.sh`, остальные впрыскиватели его повторяют;
- `editor/helix/` делает тезис о модульности структурным: видно, что именно
  нужно от редактора. **Второй адаптер не писать** — непроверенный адаптер хуже
  отсутствующего. Место сделать, `nvim` не изображать;
- три git-TUI из недочищенности превращаются в доказательство: `git_tui=gitui`
  в `modules.conf`, и слой заменился. Конфиги уже написаны, все три живут в
  `ide/` рядом (лишние симлинки безвредны);
- `profile/` вверху, а не внутри `ide/tmux/`: вкус живёт не только в tmux.
  `install.sh` симлинкует `~/.config/<name>` → `profile/`, `tmux.conf` делает
  `source-file -q ~/.config/<name>/theme.conf` — личный слой не пишется внутрь
  симлинкованного `ide/tmux/`, репозиторий не засоряется;
- `shell/` отдельно от `ide/`: zsh для работы IDE не нужен, разделение снимает
  впечатление «чтобы попробовать, надо переехать на его шелл целиком»;
- `tests/` в корне: у дотфайлов тестов не бывает — дешёвый сигнал, что это проект.

## 6. Контракты

То, что должно оставаться стабильным. Ломающее изменение здесь → строка в
`CHANGELOG.md`. Таких правок ожидается 3–4 в год.

1. **Загрузка.** `tmux.conf` в конце: `source-file -q` темы и `local.conf`,
   затем опциональные модули, затем `cyr-twins`. Последний — отложенный
   `run-shell`, поэтому двойники навешиваются и на личные бинды автоматически
   (проверить на `tmux -L test`).
2. **Данные.** Ядро не знает путей. `project` читает `profile/projects.conf`,
   дефолт — автодетект `~/code`, `~/projects`, `~/src`, `~/dev`, иначе `$HOME`.
3. **Инструменты.** Окна ищутся по имени (`=yazi`, `=lazygit`, `=search`),
   редактор — по `pane_current_command`. Выбор реализаций — `modules.conf`.
4. **Расширение.** `keys` сканирует `libexec/*` и `profile/*`: личный скрипт со
   строкой `# keys:` сам попадает в справку `C-Space ?`, ядро не трогается.
5. **Редактор.** Четыре операции: `open`, `ctx`, `reload`, `goto`.
6. **Модуль.** `modules/<name>/`: `init.sh` (загрузчик зовёт, модуль сам вешает
   хуки и бинды), опциональный `check.sh` (зовёт `doctor`), `README.md`.
   Реестра нет — ядро не знает о модулях ничего.

### Opt-in: три механизма, ни одного флага

Фича-флагов в проекте нет. То, что выглядит как флаги, — три разные сущности,
и смешивать их в один механизм нельзя:

| Что | Это на самом деле | Механизм | Где живёт |
|---|---|---|---|
| кириллица, форс-латиница | **поведение** с хуками | модуль | список в `profile/modules.conf` |
| `lazygit` / `gitui` / `tig` | **выбор** из слота | переменная | `profile/modules.conf` |
| `rga`, `bat`, `delta`, `macism` | **возможность среды** | автодетект | нигде, `command -v` |
| тема, корни проектов, бинды | **вкус и данные** | файл-оверрайд | `theme.conf`, `projects.conf`, `local.conf` |

Правило третьей строки: **если шелл может ответить на вопрос сам, не спрашивай
пользователя.** Флаг «у меня есть bat» — второй источник правды, который
протухает в день установки bat.

Следствие: **в `tmux.conf` нет условий.** Бинд висит всегда; отсутствие
зависимости обрабатывает сам скрипт — сообщение «rga не установлен: `brew
install ripgrep-all`» + `read -n1` (паттерн уже зафиксирован в
`config/tmux/AGENTS.md`). `%if`/`%endif` не появляются вовсе.

Почему не флаги: флаг заставляет ядро знать о каждой опциональной вещи по имени
(`if [ "$cyrillic" = 1 ]` где-то внутри). Это противоположность тезису проекта.
Модуль-как-каталог означает, что ядро не знает ничего, а модуль регистрирует
себя сам — разница между «написано, что модульно» и «видно, что модульно».

Рассмотрено и отклонено:

- **каталог симлинков** «включено = существует» (как `sites-enabled` у nginx) —
  честнее как единственный источник правды, но для seed проигрывает в
  читаемости: пустой каталог ничего не рассказывает, а `modules.conf` с
  закомментированным меню всех доступных модулей — самодокументируется;
- **команда `<name> module enable/disable`** — означала бы программную правку
  шелл-файла (парсинг и перезапись конфига). Модули включаются редактированием
  `modules.conf`;
- **переменные окружения как основной интерфейс** — невидимы, не находятся
  поиском, непредсказуемо переживают рестарт tmux-сервера.

Все три механизма сходятся в `doctor`: какие модули включены и какие есть, но
выключены; какие возможности найдены и что отвалится без отсутствующих;
выполнены ли требования к соседям. Это единственный честный ответ на вопрос
«почему у меня `C-Space /` не работает».

## 7. Ограничения, которые не обходим

**У helix, yazi и lazygit нет include.** Тему и настройки нельзя наложить слоем
— конфиг единый файл. Для этих тулов модель одна: форкни и правь. Обход
симлинками отдельных файлов внутрь симлинкованных каталогов кончается тем, что
личные файлы пишутся в репозиторий. Вместо обхода — список в
`docs/extending.md`: «слоями накладывается — tmux, project, модули; форкается и
правится — `ide/helix/config.toml`, `ide/yazi/theme.toml`,
`ide/lazygit/config.yml`». Это лучший аргумент в пользу рамки seed: для тулов
без include seed не компромисс, а единственная работающая модель.

**`profile/` закоммичен своим** — иначе сетап не воспроизводится на новой машине
одной командой. Следствие: у форкера при `git pull upstream` конфликты именно в
`profile/`. Лечится строкой в доках («разрешай в свою пользу»), а не архитектурой.

**macOS-only** — brew, TCC, `/Library/Keyboard Layouts`, `macism`. Сказать в
шапке README без извинений, отметить переносимые части.

## 8. Этапы

Жёсткое правило по порядку: **`tests/` пишутся до переезда.** Это ежедневный
инструмент, в день переезда он сломается целиком, а мост держится на таймингах
Escape, порядке `open → reload → goto` и протоколе `@hx_skip_reload` — вещах,
которые ломаются молча. Два-три smoke-теста проверяют переезд за минуту вместо
получаса ручного клика.

- [x] **1. Тесты.** `tmux -L test` + `capture-pane`: поднять hx на фикстуре →
      `open <file> 42` → убедиться, что файл и строка те. Плюс `reload` и
      `jump`. Интерактивный fzf так не проверить (лезет в `/dev/tty`) —
      тестировать слой данных до fzf.
- [x] **2. Переезд структуры.** Одним заходом на этой ветке: половинчатое
      состояние хуже обоих. `git mv` (история тянется через `--follow`),
      диспетчер `bin/<name>`, правка ~15 мест вызова в `tmux.conf`, keymap
      yazi, `viv-open.sh`, цикл симлинков в `bootstrap.sh`, пути сканирования в
      `keys`, оба `AGENTS.md`.
- [x] **3. Граница слоёв.** `profile/{theme,projects,local,modules}.conf`,
      `*.local` под `.gitignore` (заодно дожать `sh/parts/private` — задуман в

## 9. Безопасная поставка

Этапы 1–6 сделали проект модульным, но не сделали его **устанавливаемым на
чужую машину**. Два пункта выше про это же и закрываются здесь: §8.4 считает
«модуль клавиатуры выключен по умолчанию» сделанным, хотя дефолт ядра
(`lib/profile.sh:19`, `modules=""`) перебивается трекаемым `profile/modules.conf`,
где оба модуля включены; §10 держит открытым вопрос «публиковать `profile/`
своим или нейтральные дефолты». Это один и тот же дефект, см. принцип ниже.

### 9.1 Диагноз

`install.sh` смешивает три слоя с разной ценой ошибки:

| Слой | Куда пишет | Нужно ли ядру |
|---|---|---|
| **Ядро** — tmux-шина, `libexec`, профиль | `~/.config/zenide`, `~/.config/tmux`, `~/.local/bin/zenide` | да, это и есть zenide |
| **Соседи** — helix, yazi, lazygit, scooter, ghostty, gitui, tig, slumber, vivify | `~/.config/<tool>` ×9 | нужны **две настройки**, остальное вкус |
| **Захваты** — git, prettier | `~/.config/git`, `~/.prettierrc` | нет, к IDE отношения не имеют |

Средняя строка — ключевая. Ядро зависит не от владения чужим конфигом, а от
`auto-save.focus-lost = true` в helix и вызова `zenide open` в yazi. `doctor`
это уже проверяет и называет «требования к соседям» — то есть нужная модель в
проекте есть, но поставка про неё не знает и отбирает файл целиком.

Второй дефект — **клон одновременно софт и данные**: `install.sh` кладёт
`profile/*.local` внутрь клона, а трекаемые `profile/*.conf` служат слоем
переопределения. Две несовместимые роли в одном каталоге. Отсюда конфликты на
`git pull upstream` у форкера и потеря личного при переустановке.

### 9.2 Принцип

> **Ядро владеет только своим. У соседей оно не отбирает конфиг, а просит
> контракт и проверяет его.**
>
> **Апстрим владеет `lib/profile.sh`. Пользователь владеет `$ZENIDE_PROFILE`.
> Апстрим в `$ZENIDE_PROFILE` не пишет никогда — только раздаёт примеры.**

Второе уже наполовину сделано: `ZENIDE_PROFILE` — сквозная переменная
(`bin/zenide:27`, `project:23`, `lib/profile.sh:22`, `keys:26`), её используют
тесты и запись демо. Дыра одна: `tmux.conf:147-148` сорсит
`~/.config/zenide/profile/` абсолютным путём мимо переменной.

Вынос дефолта `ZENIDE_PROFILE` наружу от клона
(`${XDG_CONFIG_HOME:-~/.config}/zenide-profile`, fallback на
`$ZENIDE_ROOT/profile`) закрывает оба сценария сразу: у форкера апстрим и
профиль в разных деревьях — конфликт структурно невозможен; клон становится
одноразовым — снёс, клонировал заново, профиль на месте.

### 9.3 Три режима

1. **`./try` — песочница.** Полный сетап через переопределение `XDG_*` и
   `tmux -L zenide -f …`: ноль записей в `HOME`, откат — `rm -rf .sandbox`.
   Главный ответ тревожной аудитории: «попробовать» перестаёт означать
   «установить».
2. **`./install.sh` — безопасный по умолчанию.** Dry-run по умолчанию,
   применение по `--apply`; ставит только ядро; соседи по `--with helix,yazi`;
   `git` и `prettier` — отдельным явным согласием.
3. **Контракт вместо замены.** Для соседей — минимальные сниппеты для include.
   `doctor` становится спецификацией контракта, `ide/<tool>` —
   референс-реализацией.

### 9.4 Чек-лист

- [x] **1. Развязка путей.** Сделано. Конфиг поднимается из любого каталога:
      проверено запуском с подменённым `$ZENIDE_ROOT` и чужим профилем.
      Механика tmux, выясненная экспериментом (всё — на tmux 3.7b):
      · `$VAR` раскрывается в строках и в пути `source-file` при разборе;
      · `setenv -g` виден `sh` внутри `run-shell`, но **не** виден раскрытию
        `$VAR` в том же разборе — поэтому fallback в шапке работает только для
        sh-контекстов, а `source-file` считает путь через `-F` и тернарник;
      · `${VAR:-default}` **роняет весь конфиг молча** — не использовать.
      Отсюда два способа подстановки: `\$ZENIDE_ROOT` там, где строку исполняет
      sh (15 мест), формат — там, где её разбирает tmux (3 места).
- [x] **2. Профиль наружу от клона.** Сделано. Три ступени резолва живут в
      одном месте (`bin/zenide`): `$ZENIDE_PROFILE` → якорь
      `~/.config/zenide-profile` → `profile/` в клоне. Якорь ставит
      `install.sh`, и он же нужен тем, кто не умеет вычислять путь:
      `source-file` в `tmux.conf` и `include.path` в `ide/git/config` (git не
      раскрывает переменные окружения, только `~`). Реальный каталог на месте
      якоря считается внешним профилем и не сдвигается в бэкап.
- [x] **3. Нейтральные дефолты.** Сделано по уже принятому в репозитории
      образцу `projects.conf` → `projects.local`: трекаемый файл нейтрален и
      сорсит личный `*.local` из-под `.gitignore`. Так же теперь устроен
      `modules.conf` → `modules.local`. Проверено обоими профилями: с личным
      модули включены, на чистом клоне — выключены. Заодно закрывает §8.4,
      который считал это сделанным.
      Следствие, принятое сознательно: личные значения (раскладочные модули,
      корни проектов) больше не версионируются в этом репозитории. Кому нужна
      их история и синхронизация между машинами — профиль выносится в
      отдельный git-репозиторий на место якоря, см. 9.2.
- [x] **4. Детектор затенения.** Сделано: раздел «затенение» в `doctor`
      (`~/.tmux.conf` и `~/.gitconfig`), проверка из `bootstrap.sh` убрана как

      фактического `$ZENIDE_PROFILE` — чтобы «где мой профиль» не выяснялось
      чтением кода.
- [x] **5. Разметка `ide/`.** Сделано: `ide/LAYERS` — данные о слоях
      (`core` / `contract` / `slot` / `taste` / `global`) с последствием для
      каждого тула. Читают и `install.sh`, и `doctor`, так что список тулов
      нигде не продублирован. Плюс `ide/<тул>/CONTRACT*` — выжимка, которую
      достаточно врезать в свой конфиг вместо замены целиком; тест следит,
      чтобы выжимка не разошлась с полным конфигом.
- [x] **6. `install.sh --apply`.** Сделано. Без аргументов печатает план и
      выходит; проверено тестом — ноль созданных файлов. Ставит только ядро
      (`core` из `ide/LAYERS`), соседи по `--with <тул>|<слой>|all`, где `all`
      намеренно НЕ включает `global`. Невыбранные тулы печатаются с
      последствием из `LAYERS`, а уже стоящие от прошлых установок названы
      вслух — иначе «zenide их не трогает» читается как «их тут нет».
- [x] **7. Манифест и `uninstall`.** Сделано; манифест в
      `${XDG_STATE_HOME:-~/.local/state}/zenide/manifest`, снаружи клона.
      Откат проверен побайтово: чужие конфиги возвращаются из бэкапа, HOME
      остаётся чист. Грабля, на которой он сначала молча не работал: на ОДИН

## 10. Открытые вопросы

**Имя.** Выбрано: `zenide`. Критерий — находимость: `helix` или `tmux` в
имени репозитория даёт органические заходы из поиска.

**Язык UI.** Решено: пока русский. Сейчас описания `-N`, `ORDER` и `legend=` русские и видны в
`C-Space ?`. Решение можно отложить до этапа 6: строки живут в двух местах
(`tmux.conf` и `keys`), перевод — вечер работы `sed`, архитектуру не трогает.
Критерий: ценность проекта (пункты 1, 2, 7 из §2) адресована международному
helix-сообществу — значит ядро английское, цена — своя справка станет
английской. Модуль кириллицы логично оставить русским.

**Публиковать ли `profile/` своим** (тема + корни проектов без рабочих) или
отдать нейтральные дефолты. ~~Решается на этапе 3.~~ **Решено в §9.2:** ни то
ни другое — `profile/` перестаёт быть трекаемым слоем переопределения. Апстрим
раздаёт `*.example`, живой профиль живёт снаружи клона по `$ZENIDE_PROFILE`.
Вопрос «чей профиль публиковать» снимается вместе с самим каталогом.
