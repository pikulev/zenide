# zenide + дотфайлы одной машины

Терминальная IDE: Helix в центре, tmux как шина IPC, yazi / git-TUI / scooter
как заменяемые слои. Вокруг — личные дотфайлы macOS.

**Сначала прочитай [docs/architecture.md](docs/architecture.md)** — там тезис,
контракты и протокол инъекции в редактор. Грабли, которых не видно из кода, —
[docs/pitfalls.md](docs/pitfalls.md). Эти два файла не дублировать: правка
механики идёт туда же.

Поставка (симлинки и их потребители, резолв профиля, роль `ide/` и `LAYERS`,
обратимость) — [docs/onboarding.md](docs/onboarding.md). Правка установщика
или слоёв идёт туда же, дублировать в README не нужно.

## Правила работы

- Не коммитить и не пушить. Коммитит и ревьюит владелец; ты правишь и показываешь diff.
- Сомневаешься в правке — сначала предложи, потом делай.
- Git: только merge. Никаких rebase/squash/fixup/переписывания истории; откат опубликованного — `revert`.
- Стиль коммитов (если попросят): `feat(scope): …` / `fix(scope): …`, можно по-русски.
- Общение и комментарии в конфигах — по-русски.
- Простое ручное решение предлагать раньше скрипта-интеграции.

## Главное правило размещения

**Это механика или вкус?** Вкус, личное, пути, идентичность → `profile/`.
Механика, соглашение, протокол → `libexec/` или `ide/`. Не можешь решить →
`profile/`: ядро должно оставаться маленьким, ошибка в эту сторону дешевле.

```
libexec/zenide/   механика: подкоманды. Личных данных быть НЕ ДОЛЖНО
  editor/helix/   слот редактора: ровно четыре операции open·ctx·reload·goto
ide/<tool>/       конфиги тулов → симлинки ~/.config/<tool>. Править только здесь
modules/<name>/   выключаемое поведение: init.sh + опц. check.sh + README.md
profile/          вкус и данные; *.local под .gitignore (identity, рабочее)
shell/            zsh: parts/ + ЯВНЫЙ список в zshrc.sh (не глоб)
tests/            headless, сокет zenide-test
attic/            легаси, не трогать
```

## Где что править

- Новая подкоманда — исполняемый файл в `libexec/zenide/`. Диспетчер списка не
  содержит, `zenide help` выводит описание из ПЕРВОЙ комментарной строки.
- Перекрёстные вызовы между подкомандами — только через диспетчер по
  установленному пути: `~/.config/zenide/bin/zenide ctx`. Не через PATH (в
  попапах tmux он не гарантирован) и не относительными путями.
- Личные команды шелла — исполняемый файл в `shell/bin/` (на PATH через
  `shell/parts/bin.sh`), а не алиас.
- Новый фрагмент шелла — файл в `shell/parts/*.sh` + строка в явном списке
  `shell/zshrc.sh`. `~/.zshrc` руками не трогать.
- Новый пакет: нужен для работы сетапа — `Brewfile` (ядро, держать коротким),
  иначе — `Brewfile.full`. Но рантайм или тул из npm/pypi/cargo — НЕ brew, а
  `ide/mise/config.toml`: версия тогда пинится, а не «что сейчас в brew».
  Исключение — rustup: тулчейны и компоненты умеет только он.
- Новый шаг установки: симлинки и профиль — `install.sh` (часть проекта);
  личное окружение — `bootstrap.sh`. Идемпотентно, сетевое обернуть в `try`.
- Пути только через `$HOME` / `$ZENIDE_*` / `$SHELL_CONFIG_ROOT`. Хардкод
  `/Users/...` запрещён — сейчас таких нет, не заводить.
- Любой свой tmux-бинд обязан иметь `-N "группа: описание"`, группа — из
  `ORDER` в `libexec/zenide/keys`. Без заметки клавиша выпадает из справки
  `C-Space ?` МОЛЧА (тест `t-config.sh` это ловит).

## Фича-флагов нет

Три разные сущности — три механизма, не смешивать:

- **выбор** из слота (`git_tui`, `editor`, `files`, `search`) — переменная в
  `profile/modules.conf`;
- **поведение** с хуками — модуль в списке `modules`; ядро не знает о модулях
  по именам, никаких `if имя_модуля`;
- **возможность среды** (`rga`, `bat`, `delta`, `macism`) — НЕ настройка:
  `command -v` в рантайме. Если шелл может ответить сам, не спрашивай
  пользователя.

Следствие: **в `tmux.conf` нет условий.** Бинд висит всегда; отсутствие
зависимости обрабатывает скрипт — сообщение + `read -n1` (в попапе
`display-message` не успеют прочитать).

## Стиль

- Тема везде Monokai Pro Spectrum: bg `#222222`, fg `#f7f1ff`, dim `#69676c`,
  selection `#525053`. Другие темы не предлагать. Палитра tmux — только в
  `profile/theme.conf`, в ядре цветов быть не должно.
- UI сдержанный: без скруглённых капсул и powerline-глифов, селекты тусклые,
  цвет только по смыслу.
- В темах — только hex (см. грабли про ANSI и оранжевый `blue`).
- Lua — минимум: маленькие сниппеты в yazi ок, новую логику на Lua не писать.

## Проверка

`./tests/run.sh` — обязательно после любой правки механики. Всё на сокете
`zenide-test`, живая сессия владельца не трогается. Дальше:

- `zenide doctor` — слоты, зависимости, требования к соседям;
- `tmux source-file ~/.config/tmux/tmux.conf`; TUI headless — `tmux -L test` +
  `capture-pane`;
- `hx --health <lang>`; `yazi --help` (парсит конфиг, ошибка видна сразу);
- шелл-скрипты — `shellcheck` (гоняется в `tests/t-lint.sh`); версия запинена
  в `mise.toml`+`mise.lock` репозитория, поставить — `mise install`;
- в macOS нет `timeout` → `perl -e 'alarm N; exec @ARGV'`.

Попапы с fzf прогоняются целиком — см. `tests/t-popups.sh`. Запускать fzf
НАПРЯМУЮ из своего шелла действительно нельзя (нет tty, глохнет на SIGTTIN),
но внутри tmux-пейна pty есть, поэтому попап работает, а `capture-pane`
показывает его содержимое. Ждать готовности по промпту недостаточно: у
попапов со списком — по счётчику fzf, у live-grep — по промпту (список пуст
до ввода). Чего проверить не можешь (GUI, TCC) — так и скажи.
